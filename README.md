# Проверка условий договоров поставки

Прототип для специалиста по закупкам. Он загружает TXT-документы по договорам поставки и показывает по каждому договору поставщика, сумму, срок поставки и ставку неустойки на дату проверки. У каждого значения есть основание: имя файла, точная цитата и переход к абзацу исходного текста.

## Запуск

Нужен только Python 3.9 или новее. Сторонние пакеты программе не нужны, устанавливать ничего не требуется.

```bash
python3 app.py
```

После запуска откройте http://127.0.0.1:8000. Другой порт: `python3 app.py --port 9000`. В Windows команда называется `python` вместо `python3`.

Проверки:

```bash
python3 -m unittest discover -s tests -v
```

## Приложения для macOS и Windows

Та же программа в собственном окне, без браузера и командной строки. Обе оболочки устроены одинаково: запускают программу на свободном порту своего компьютера, показывают её страницу в окне и завершают её при закрытии окна. Правила и сведение условий остаются в `contractcheck/` и в оболочках не дублируются.

| | macOS | Windows |
|---|---|---|
| Исходный код оболочки | `macos/main.swift` | `windows/main.py` |
| Сборка | `./macos/build.sh` | `windows\build.bat` |
| Результат | `dist/Проверка договоров.app` | `dist\ContractCheck.exe` |
| Нужно для сборки | Xcode Command Line Tools | Python 3.9+ и интернет: ставятся pywebview и PyInstaller |
| Нужно для запуска | Python 3 (входит в Command Line Tools) | ничего: Python вложен в файл. Окно использует WebView2, он есть в Windows 10 и 11 |

Самопроверка сборки открывает окно, загружает учебные файлы и читает таблицу: `./macos/build.sh --check` на macOS, `dist\ContractCheck.exe --selftest` на Windows (итог пишется в `selftest.txt`).

При каждой отправке в репозиторий GitHub Actions прогоняет тесты на Linux, Windows и macOS и собирает оба приложения. Готовые приложения можно скачать со [страницы релизов](https://github.com/vkarateev80/TEST-HH/releases/latest): `ContractCheck-Windows.exe` и `ContractCheck-macOS.zip` (для Mac с процессорами Apple Silicon и Intel).

Приложения не подписаны сертификатом разработчика. Скачанный файл Windows откроет после предупреждения SmartScreen («Подробнее» → «Выполнить в любом случае»), macOS — после подтверждения в настройках безопасности. Приложение, собранное на своём компьютере, запускается без предупреждений.

## Как пользоваться

1. Перетащите TXT-файлы в область загрузки или нажмите «Выбрать файлы». Кнопка «Учебные файлы из папки documents» загружает все TXT из папки `documents` — это то же самое, что выбрать их вручную.
2. Таблица «Условия договоров» показывает номер, поставщика, сумму, срок поставки и ставку неустойки на дату проверки. Дата задаётся в правом верхнем углу, по умолчанию 10.03.2026 (дата из задания).
3. Под каждым значением стоит цитата и ссылка вида `02_amendment_signed.txt, абз. 6`. Нажатие открывает документ в панели «Исходный текст» на нужном абзаце с подсвеченной цитатой.
4. Если значение изменено допсоглашением, это написано в ячейке: чем изменено, с какой даты и что было раньше.
5. Раздел «Не учтено в таблице» перечисляет предложения из писем, проекты и ещё не вступившие в силу соглашения.
6. Раздел «Вопросы»: выбор договора и поля даёт ответ с основанием, фильтр «Поставка раньше даты» — список договоров и неучтённые изменения срока.

Четыре вопроса из задания:

| Вопрос | Как получить | Ответ на учебных файлах |
|---|---|---|
| Срок поставки по STN-101 на 10.03.2026 | Договор STN-101, поле «Срок поставки» | 30.04.2026, изменён допсоглашением № 1 |
| Сумма договора STN-102 | Договор STN-102, поле «Сумма договора» | 840 000 ₽ |
| Сумма договора STN-103 | Договор STN-103, поле «Сумма договора» | нет данных: стоимость задана приложением, которого нет в комплекте |
| Поставка раньше 01.04.2026 и несогласованные изменения срока | Фильтр «Поставка раньше даты» | STN-102 (20.03.2026); есть несогласованное предложение перенести срок на 27.03.2026 |

## Известные ограничения

- **Формат документов.** Правила рассчитаны на учебный формат: тип документа в первой строке, строка «Статус: …», один пункт — одна строка. Суммы пишутся цифрами со словом «руб», даты — как `15.04.2026` или `15 апреля 2026`.
- **Типы документов.** Распознаются договор, допсоглашение, проект допсоглашения и письмо. Остальное попадает в раздел «не удалось связать с договором».
- **Поля.** Извлекаются поставщик, сумма, срок поставки и ставка неустойки.
- **Неустойка.** Берётся ставка за просрочку поставки. Предел («не более 10%») отдельным полем не выделяется и виден в цитате. Неустойка за просрочку оплаты не учитывается.
- **Формулировки изменений.** Понимаются «изложить в следующей редакции: «…»» и «изменить … на …». Изменение на величину («увеличить на 70 000 рублей») не пересчитывается, а помечается «требует проверки».
- **Статус подписания** берётся из текста документа. Прототип не проверяет подписи и не обращается к внешним системам.
- **Хранение.** Ничего не сохраняется: тексты живут в памяти страницы до её закрытия. Приложение локальное, без входа и прав доступа.
- **Приложения для macOS и Windows.** Не подписаны сертификатом разработчика. Перетаскивание файлов в окно приложения для Windows не проверялось, кнопка «Выбрать файлы» работает через стандартное окно системы.
- **Вне объёма:** PDF, DOCX, сканы, расторжение договора, смена поставщика допсоглашением, валюты кроме рубля.

Если формулировка не распознана, прототип показывает «нет данных» или «требует проверки», а не подставляет значение.

## Записка

### Для кого

Специалист по закупкам, который ведёт несколько договоров поставки и перед оплатой, приёмкой или претензией сверяет действующие сумму и срок. Сейчас для этого он перечитывает договор и всю переписку к нему. Прототип отвечает на вопрос «что действует сегодня и на основании какого текста».

### Пять вопросов клиенту перед развитием

1. Какие решения принимаются по этим данным и сколько стоит ошибка в сумме или сроке? От этого зависит требуемая точность и объём ручной проверки.
2. В каком виде приходят документы (сканы, DOCX, выгрузка из СЭД, почта) и сколько разных шаблонов договоров используется?
3. Что считается источником правды о подписании: текст документа, СЭД или ЭДО, реестр договоров?
4. Какие ещё условия нужны и в каком порядке: условия оплаты, аванс, спецификации, гарантийные сроки?
5. Куда должен попадать результат (Excel, ERP, отчёт руководителю), сколько договоров и пользователей, кто какие договоры имеет право видеть?

### Допущения

- Условия меняет только допсоглашение, подписанное обеими сторонами и вступившее в силу к дате проверки. Письма и проекты показываются отдельно.
- Имя файла, дата загрузки и порядок загрузки на результат не влияют.
- Документ относится к договору, номер которого указан в его заголовке или тексте.
- Сумма договора — это общая стоимость. Аванс и лимит бюджета суммой не считаются.
- «Раньше 1 апреля» означает строго раньше; сравнивается срок, действующий на дату проверки.
- Подписанное допсоглашение без даты вступления в силу не применяется, а отправляется на проверку.

### Две метрики

1. **Точность по полям на размеченной выборке договоров.** Отдельно считается доля выдуманных значений: показано число там, где по эталону «нет данных» или другое значение. Целевое значение этой доли — ноль.
2. **Время проверки одного договора** до и после внедрения, а также доля значений со статусом «требует проверки»: она показывает, сколько работы остаётся человеку.

### Архитектура

```
Браузер (static/)  ──  POST /api/analyze {тексты файлов, дата}  ──▶  app.py  ──▶  contractcheck/
   таблица, вопросы,                                                               textutil.py  абзацы, даты, суммы
   панель исходного текста  ◀──────────  отчёт (JSON)  ◀───────────────────────    rules.py     правила полей
                                                                                   document.py  один документ
                                                                                   report.py    сведение условий
```

Приложения для macOS и Windows — тонкие оболочки: окно, внутри которого открыта та же страница, и запуск того же `app.py`.

Обработка идёт в четыре шага: текст делится на пронумерованные абзацы; по документу определяются тип, номер договора, статус и значения полей; документ связывается с договором и получает роль (учтён, ещё не действует, не согласован, требует проверки); по каждому полю берётся значение договора и поверх него применяются учтённые допсоглашения в порядке вступления в силу.

### Три технических решения и их компромиссы

1. **Правила вместо языковой модели.** Результат одинаков при каждом запуске, цитата вырезается из исходного текста по позиции, не нужны ключи и сеть. Цена: правила привязаны к формулировкам. Незнакомая формулировка даёт «нет данных» или «требует проверки», а не ошибочное значение.
2. **Сервер без состояния.** Каждый запрос пересчитывает отчёт по присланным текстам. Это просто, не требует базы и позволяет менять дату проверки мгновенно. Цена: нет истории и совместной работы, подход годится для десятков документов.
3. **Поле как описание, а не как код.** Каждое поле задано одним объектом `FieldRule` в `rules.py`; сведение условий и таблица в интерфейсе работают со списком полей. Новое поле добавляется правилом и тестом: ставка неустойки потребовала правку `rules.py` и `textutil.py`, а сведение условий и интерфейс не менялись. Цена: поля со сложной структурой (график поставок, спецификация) в эту схему не укладываются.

### Что изменится при 100 000 документов и правах доступа

- **Хранение.** Документ разбирается один раз при загрузке. Найденные значения с адресом (документ, абзац, позиция, версия правил) кладутся в базу; при новом документе пересчитывается только его договор.
- **Связывание.** Нужен индекс по номерам договоров и контрагентам и сопоставление разных написаний одного контрагента. Обработка уходит в фоновую очередь.
- **Извлечение.** Формулировок станет слишком много для ручных правил. Появится извлечение моделью с обязательной проверкой: значение принимается, только если оно дословно найдено в указанной цитате. Сомнительные случаи идут в очередь ручной проверки.
- **Права доступа.** Права наследуются от исходных документов и проверяются на каждом запросе, включая цитаты. Если допсоглашение пользователю недоступно, нельзя молча показать ему устаревшее значение: нужно сообщить, что есть документ вне его прав. Нужен журнал обращений.

### Три следующих улучшения по приоритету

1. Условия оплаты и аванс тем же механизмом правил.
2. Проверка на реальных договорах клиента: размеченная выборка, измерение точности, расширение правил или извлечение моделью для незнакомых формулировок.
3. Выгрузка таблицы с источниками в Excel и приём PDF и DOCX.

## Отчёт о вайбкодинге

**Инструмент:** Claude Code (приложение для macOS). Внутри самого прототипа модель не используется.

**Характерные запросы.** Спецификацией служил файл с заданием и шесть учебных документов, поэтому сами запросы были короткими:

1. «Изучи папку» — ИИ прочитал задание и документы, перечислил требования, ожидаемые ответы на четыре вопроса и ловушки в данных (аванс, срок оплаты, лимит бюджета, неподписанный проект).
2. «Сначала обсудим стек» — ИИ предложил Python без зависимостей и правила вместо модели, сравнил со Streamlit, Flask, вариантом целиком в браузере и вариантом с моделью.
3. «Да, делаем» — ИИ написал разбор документов, сведение условий, тесты, сервер и интерфейс, затем проверил сценарий в браузере.
4. «Сначала неустойку» — ИИ добавил правило для ставки неустойки и семь тестов к нему. Колонка в таблице и пункт в вопросах появились без правки интерфейса.
5. «Сделай нативное приложение… для винды и для маку» — ИИ написал две оболочки с окном (Swift для macOS, Python с pywebview для Windows), скрипты сборки, самопроверку сборки и проверку на GitHub Actions.

**Ошибки ИИ и как они найдены.**

- *Тип документа определялся по слову «договор» в любом месте первой строки.* Заметка «Заметка по договору STN-200…» стала строкой таблицы без номера и условий. Ошибку поймал тест `test_unknown_document_type_is_listed_for_review`. Исправление: тип определяется по началу заголовка, такая заметка попадает в список «требует проверки».
- *На узком экране таблица растягивала страницу по горизонтали.* Найдено при проверке в браузере на ширине 375 пикселей. Исправление: таблица прокручивается внутри своей карточки.
- *Переход к источнику прокручивал всю страницу, а не панель с текстом.* Найдено при проверке в браузере, исправлено.
- *В исходном коде вместо записи `\u00a0` оказались сами невидимые символы (неразрывные пробелы).* Код работал, но такой текст нельзя надёжно читать и править. Обнаружилось, когда очередная правка не нашла ожидаемую строку. Исправление: в коде восстановлена явная запись.

**Как проверялся результат.** 43 автоматических теста: четыре вопроса из задания; ставка неустойки; точность цитат (каждая цитата дословно содержится в своём абзаце); ловушки; отсутствующие значения; статусы документов; независимость от имён и порядка файлов; работа сервера. В браузере пройдены загрузка семи файлов через поле выбора (включая новый договор в кодировке Windows-1251 и пропуск PDF), смена даты проверки на 28.02.2026 (по STN-101 вернулись исходные условия), переход к абзацу и колонка неустойки. Оба приложения проверены встроенной самопроверкой (окно открывается, таблица строится): для macOS — на своём компьютере и в GitHub Actions, для Windows — в GitHub Actions; там же тесты проходят на Linux, Windows и macOS. Вручную на компьютере с Windows приложение не запускалось.
